# 申報資料檢核助手 · Finance & Actuarial Validation Assistant

THEME 6 | Finance, Actuarial & Data Management — **6-2 資料品質與檢核助手**

## 情境：法規申報與精算/財務數據大表匯入

財務與精算部門定期要向金管會、保發中心申報大量財務報表、準備金與精算資料。資料來自銷售、理賠、投資等多個上游系統，格式複雜、檔案龐大，人工對帳往往要好幾天；一旦被退件，通常只拿到籠統的錯誤代碼，要在數萬筆資料裡重新翻找。

本工具在匯入/申報**之前**，依既定檢核規則全自動驗證資料，並把每個問題定位到「哪個檔、第幾行、哪個欄位、應該改成什麼」。

| 痛點 | 本工具的做法 |
|---|---|
| **1. 跨系統整併的時間差斷層**：各系統結帳時點、口徑不同，金額兜不攏，只能人工比對 | **上游控制總數對帳**：申報明細依各系統口徑彙總，與新契約、理賠、保單管理系統的控制總數逐期比對。有差異時自動歸因：**時間差**（找出落在結帳邊界、金額恰好等於差額的那幾筆，例如 12/30 給付被理賠系統算到次年 1 月）、**定義差**（例如外幣保單以原幣加總）、或**待查**（找不到可解釋的原因，並連結相關的明細錯誤）。時間差與定義差只需在對帳底稿說明，不必改申報檔 |
| **2. 跨欄位計算矛盾、代碼錯置**：加總不平、期初期末結轉兜不攏、使用錯誤或已失效的代號 | **財報勾稽**：期初 + 增加 − 減少 = 期末、上層 = 下層合計、資產 = 負債 + 權益，並做**根因串連**——同一個差額出現在多個檢核時，指出唯一的源頭（例：責任準備金一個數字對調 → 保險負債、負債總計、資產負債表不平共 4 個錯誤，修一處全解）。**停用科目**（如 IFRS 9 後停用的「備供出售金融資產」）提示替代科目；**代號錯置**（1401 打成 1410）比對數字對調/誤植，推薦正確代號。<br>**期初/期末結轉**：上年度申報檔期末 vs 本年度期初逐保單勾稽（漏報、保額不一致），並產出保額變動表，找出「保額變了卻沒有對應異動」的保單。<br>**明細檢核**：依填報手冊 257 條規則檢查格式、代碼（含商品類別編號編碼原則）、單筆與多筆邏輯、承保與給付跨檔 |
| **3. 退件的黑盒子**：只給「錯誤代碼 10400：數字資料範圍錯誤」，不知道錯在哪一列 | **退件解碼**：貼上退件訊息，辨識手冊檢核編號（新舊編號皆可，如 `30212_L1305`、`L0612`）、行號、欄位名稱；手冊「肆、檢核程式項目及代碼表」的錯誤代碼（如 10400 數字資料範圍錯誤）列出該代碼下所有欄位的問題；其他籠統代碼（如自訂的 `E-0504`）依代碼前綴或關鍵字推定錯誤類別。依目前資料重新檢核後，列出所有具體位置與修正值，並可請 AI 解讀退件訊息、擬定修正順序 |

另外：
- **資料邏輯合理性（疑似異常）**：資料合法、但不太合理的情況標為「疑似異常（需人工判斷）」，不計入錯誤：新契約投保年齡超過 80 歲（A001）、保額／應繳總保費比與同商品中位數相差 5 倍以上的統計離群（A002）、生效後 180 天內身故／失能／末期給付（A003）、同一被保險人 365 天內多次身故／失能／末期給付（A004，有客戶資料時以證號辨識同一人）。理賠發生日早於生效日由手冊規則 26600_D1002 判為錯誤；投保年齡超過 100 歲、保額超過 5 億、總保費大於保額 3 倍等由 X002–X004 以警告呈現
- **修正建議與自動修正**：每項問題都有建議；可推得正確值的（年滿期迄日、異動序號、補前置 0…）看過說明後逐筆套用（不提供整批自動修改），下載修正後檔案
- **檢核報告**：獨立 HTML 報告（含對帳與財報章節）、問題清單 CSV、保發中心風格的不符資料檔
- **AI 分析（Claude）**：把明細錯誤、對帳差異、財報問題一起歸納成系統性根因，區分「要改申報檔」與「只需在底稿說明」，排出修正優先順序並評估退件風險

### 客戶資料與商品資料

題目點名的四類模擬資料（保單、理賠、客戶、公開保險商品）都有對應檢核：

- **客戶資料**（要保人、被保險人）：身分證／居留證檢查碼、性別與證號第 2 碼、郵遞區號與地址的縣市區是否一致、同一證號的姓名／生日／性別是否一致；並與承保檔比對被保險人生日、性別及「被保險人身份」（本人時兩者須為同一證號、子女須比要保人年輕）。**承保檔欄位不合法而客戶資料正確時，直接以客戶資料作為建議修正值**，確認後套用。
- **商品資料**：商品代號是否存在（打錯時推薦相近代號）、起保日晚於停售日仍用舊代號（給替代代號）、起保日早於起售日、險種與商品類別編號、繳費年期。

### 試用 Excel 活頁簿

`samples/excel/` 內有兩本活頁簿，可直接拖進工具任一上傳格，依工作表名稱自動分配：

- `試用資料_含錯誤.xlsx`：保單資料、理賠資料、客戶資料、商品資料、去年保單資料、系統總數、資產負債表，以及「錯誤解答」（68 項刻意放入的錯誤與 4 筆「請人工判斷」案例）。舊名稱（承保資料、給付資料、上年度承保資料、控制總數）的活頁簿也能讀。
- `試用資料_正確.xlsx`：同樣結構的正確資料，檢核結果應為 0。

另有一組規模較接近實務的 `試用資料_1000張_含錯誤.xlsx`／`_正確.xlsx`：1,269 列保單資料，錯誤約佔 5%，險種代號與保單號碼為一般格式（重新產生：`npm run workbook:large`）。

數字欄位以文字儲存、保留前置 0；資產負債表的上層科目是 `SUM` 公式，「說明」工作表附平衡檢查公式。重新產生：`npm run workbook`（最後一步用 LibreOffice 重算公式；沒有 LibreOffice 時，請用 Excel 開啟並存檔一次，否則上層科目會是空白）。

### 規則匯入：上傳規則文件，由 AI 轉成可執行規則

主辦單位或公司內部的檢核規則文件（PDF、Word、文字檔）可以直接上傳。流程：

1. **讀取文件**：在瀏覽器內擷取文字（PDF 用 pdf.js、Word 用 mammoth），檔案不會上傳。長 PDF 會自動建議檢核條文最集中的頁數（例如《檢核規則_2025》建議第 46–63 頁）。
2. **Claude 轉換**：分段送給 Claude，附上兩個申報檔的欄位字典與規則格式說明，轉成 JSON 規則。規則是宣告式條件（欄位、比較、日期與金額函式、同保單上一筆），**不執行任何 AI 產生的程式碼**。
3. **自動審核**：每條規則先做格式驗證（欄位存在、運算合法），再在「正確範例資料」上試跑。在正確資料上就觸發的規則標為「疑似轉錯」，與內建規則同編號的標為「與內建相同」，預設都不勾選。
4. **人工確認後套用**：卡片上並列原文、規則的中文說明（「當…必須…」）與目前資料的不通過筆數。勾選套用後與內建規則一起執行，結果出現在明細檢核，類別為「匯入規則」。規則可下載成 JSON 保存、再匯入。

內附兩份範例文件：「公司內部核保規則」（內建檢核沒有的規則，例如 3,000 萬元以上新契約須體檢、75 歲以上不得承保終身壽險），以及「填報手冊檢核條文節錄」（可與內建規則對照，驗證轉換正確性）。沒有 AI 可用時，可按「載入預先轉換結果」展示完整流程。

### 規則引擎與 AI 的分工

判定對錯一律由規則引擎執行：結果可重現、可稽核，每一項都能對回手冊條文或科目表。AI 負責**解讀**：歸納根因、排定優先順序、把籠統的退件訊息翻成具體行動。AI 產生的內容在畫面與報告中都標示「AI 產出」；每個會呼叫 AI 的按鈕旁都有「此功能會將內容傳送至 Claude API」提示。

送出內容一律由 `src/ai-payload.js` 組成，並以 `src/pii.js` 遮罩個資：

| 個資 | 偵測方式 | 遮罩後 |
|---|---|---|
| 身分證／居留證 | 資料中的證號，以及英文字母＋1/2/8/9 或兩個英文字母開頭的 10 碼（不分大小寫） | `***`（完全替換） |
| 姓名 | 客戶資料中的姓名；「姓名：」「要保人：」等標示後的姓名 | `王○明` |
| 地址 | 縣市＋鄉鎮市區開頭的地址；沒有縣市但有路／街＋門牌號的地址；村里鄰 | `臺北市信義區[已遮蔽地址]`、`[已遮蔽地址]` |
| 電話 | 手機（含 +886）、有區碼的市話（含分機） | `***` |
| Email、卡號、帳號 | Email、4 碼一組的卡號、「帳號：」後的數字 | Email `***`、卡號 `****-****-****-1234`、`[已遮蔽帳號]` |

保單號碼、賠案號碼等外觀像證號的代碼，只要出現在申報資料的對應欄位就保留，AI 才能對應到是哪一筆。**送出前的最後關卡**（`src/ai.js`）：所有送出文字再遮罩、再掃描一次，仍偵測到疑似個資就停止送出（不會「漏過去」）；畫面會顯示這次遮蔽了哪幾類、各幾處。`tests/pii.test.js` 驗證各類遮罩、不誤遮金額／日期／代碼，以及三個險種的試用資料送出內容掃描不到任何個資。

| 功能 | 實際送出 |
|---|---|
| AI 整理重點 | 可以寫檢查條件的欄位清單 (只有欄位代號與名稱，不含資料)；檢核摘要（筆數、各類別次數）；前 25 條規則的編號、名稱、嚴重度、次數、一則範例訊息與建議；前 80 筆問題的檔別、行號、保單號碼、檢核編號、欄位名稱、欄位值、訊息；對帳差異（系統、期間、差額、判定）；結轉問題；前 40 筆客戶／商品問題（訊息中的姓名、證號、地址已遮罩）；財報勾稽問題 |
| 請 AI 用白話解釋 | 該問題的編號、名稱、依據、訊息、欄位值、建議、同編號筆數；**只送問題欄位與背景欄位**（保單序號、異動序號、保險期間、加退保別與日期、商品類別／代號、起迄日、幣別、繳費別與期間、給付類別、發生／給付日），不送證件編號、出生日期、性別、郵遞區號、身心障礙、經濟弱勢、職業代碼等其他欄位（除非該欄位就是問題本身） |
| 看懂退件通知 | 使用者貼上的退件訊息；每條線索的定位結果（每組最多 3 筆：位置、保單號碼或科目、值、訊息、建議） |
| 新增檢查規則 | 規則文件文字（分段）、兩個申報檔的欄位字典與規則格式說明；不含申報資料。文件中若出現身分證號、姓名、地址、電話、Email 也會遮罩 |

**AI 的結論要經過驗證**（`src/ai-verify.js`）：AI 整理重點時，每個共同原因都要附上可以檢查的條件（規則格式的 JSON，不能執行程式）。工具用原始資料逐筆計算，標示「已驗證」「原因成立、數字不對」「不成立」「無法驗證（推測）」，筆數一律以工具算出的為準，並寫進報告與稽核軌跡。其他 AI 判斷也一樣：退件可能性由工具判定後比對；修改順序的理由（影響最多、有建議修正值、會連帶其他錯誤）用數字檢查；預防檢查拿現在的資料試跑，算出抓到幾筆、誤報幾筆，可加入成為自訂檢查；單筆解釋建議的正確值改進資料副本重新檢查；退件說明的原因核對定位結果。

**改用公司自建 AI 平台（Dify）**：工具介面不再提供使用者自行設定 Dify；改為部署時的選項——部署者在 `config.local.js` 設定 `window.DQ_AI_CONFIG = { provider: 'dify', url, proxy: true }`，由公司轉發伺服器加上金鑰（前端不帶金鑰）。送出前遮蔽、確認內容與結果驗證都相同。建立步驟與要貼進去的提示詞見 `docs/dify-setup.md`。

AI 說明**不需要 API key**：只在 claude.ai 的線上版提供，使用開啟者自己的 Claude 帳號（第一次使用時會詢問是否允許）。在自己電腦上直接開啟 `index.html` 時沒有 AI，按鈕會說明原因；其他檢查功能都能正常使用，規則匯入也可以用「使用範例的轉換結果」展示。

## 部署到 Vercel

這是純前端的靜態網站，不需要建置或伺服器，`vercel.json` 已設定好（不安裝套件、不建置、直接提供整個資料夾；`sw.js` 與法規更新包不快取，確保大家拿到最新版）。

- **連結 GitHub（建議）**：在 vercel.com 選「Add New → Project」，匯入這個 repository，按「Deploy」。之後每次併入 main 都會自動更新網站。
- **用命令列**：安裝 Vercel CLI（`npm i -g vercel`）後，在專案資料夾執行 `vercel`（預覽）或 `vercel --prod`（正式）。
- **上傳壓縮檔**：執行 `sh tools/build-zip.sh`，產生只含執行所需檔案的 `dist/filing-validation-assistant.zip`（1MB 以下，不含試用資料與測試），解壓縮後可直接部署，或雙擊 `index.html` 使用。

部署後檢核工具在網站根目錄（`/`），使用說明在 `/docs/guide.html`，介紹頁在 `/docs/`。

## 介面

檢核工具（`index.html`）是給外部使用者直接使用的：打開時不載入任何資料，也沒有範例按鈕，只顯示拖放框（可放入申報文字檔或 Excel；只有標題列的工作表會被當成沒有資料）。展示時把 `samples/excel/` 的模擬資料拖進去即可看到完整結果。工作台版面：深色頂部導覽列（右側顯示已檢查幾筆、沒有必須修改問題的比例）→ 把 Excel 拖進上方大框（放入後縮成一列）→ 四張統計卡片（必須修改、建議確認、請人工判斷、有建議值）→ 左側問題清單、右側問題說明（問題、建議修正方式、依據的規定三段，底部「改成建議的值」）。清單可依狀況、資料篩選與搜尋，點一項看右側說明；那一行的原始資料預設收合，摘要標出出問題欄位的字元位置，例如「顯示原始資料（第 61–68 字）」）→ 下載問題清單、下載報告、下載改好的保單資料。數字核對明細、看懂退件通知、新增檢查規則、預覽報告、檢查項目一覽收在頁尾的「進階功能」。

**逐筆確認（手機版）**：在「更多」選單按「逐筆確認」，一次看一個問題——大卡片顯示有問題的值與位置，下方大按鈕選「改成建議的值」或「先不改／記下來」，上方有分段進度條；最後一次套用選擇的修改並可下載。手機（720px 以下）預設以逐筆確認為主、清單收起；電腦上也可以使用。

配色為暖色淺底（米白紙張底、暖墨色文字、磚紅色主要按鈕），電腦與手機同一套、只有淺色；字體一律思源黑體。

**使用說明**：工具首頁（還沒放資料時）有三步驟說明與「完整使用說明」卡片，頁首右上與頁尾也有連結，說明頁在 `docs/guide.html`（準備資料、看懂結果、修改與下載、手機使用、進階功能、法規更新、資料安全、常見問題、支援範圍）。

## 放入資料沒有反應時

- **畫面上方出現紅框「工具沒有完整開啟」**：`index.html` 旁邊找不到 `src`、`rules`、`vendor` 資料夾。常見原因是直接在壓縮檔裡點開，或只複製了 `index.html`。請先解壓縮整個資料夾再開啟。
- **讀不了 Excel**：讀 Excel、PDF、Word 的元件都放在 `vendor/`，和工具同一個網站提供；只複製了 `index.html`、沒有 `vendor` 資料夾時會讀不了。
- 支援 `.xlsx`、`.xls`、`.xlsm`、`.ods`；工作表名稱不是預設名稱（例如 Sheet1）時，會依第一列的欄位名稱判斷是哪一份資料。
- CSV、文字檔先用 UTF-8 讀，失敗時自動改用 Big5（Windows 的 Excel「另存 CSV」預設是 Big5）。
- 只放了客戶、商品等資料、沒有保單或理賠資料時，會提示還缺什麼，不會顯示「0 個問題」。
- 檔案沒拖進框內也會讀取，不會讓瀏覽器直接打開那個檔案。

## 用語

畫面、報告與 Excel 一律使用白話（對照表在 `src/labels.js`）：錯誤／警告／疑似異常分別顯示為「必須修改／建議確認／請人工判斷」；問題類別如「單筆邏輯」顯示為「同一筆資料前後矛盾」；和系統總數比對的「時間差／定義差／待查」顯示為「結帳日不同／算法不同／需要追查」。檢查程式內部仍使用原本的名稱。

## 下載的檔案

下載檔名一律用英數字（`issues_list.xlsx`、`check_report.html`、`reject_LFL01_2025.txt`、改好的 `LFL01_2025.txt`），因為有些瀏覽器會丟掉中文檔名、存成沒有副檔名的「download」，打開就變亂碼。問題清單下載為 Excel 檔；Excel 元件無法載入時改下載 CSV（含 BOM 與 Windows 換行，Excel 可正確顯示中文）。

## 快速開始

直接雙擊 `index.html` 用瀏覽器開啟（不需要伺服器或安裝），把 Excel 拖進上方的框（展示用的模擬資料在 `samples/excel/`，例如 `試用資料_含錯誤.xlsx`，7 張工作表）。所有檢核都在瀏覽器內執行，資料不會上傳；試用資料與規則都內嵌在 JS 檔裡。讀 Excel、PDF、Word 的元件放在 `vendor/`，不需要連網。

- 結果表列出工作表、行號（由 Excel 匯入時為 Excel 列號）、欄位、原始值、錯誤說明與建議修正值，可依嚴重度（錯誤／警告／疑似異常）、工作表、類別篩選；能推得正確值的提供建議值，逐筆確認後套用。
- 自動測試：雙擊 `tests/run.html`，確認含錯誤版的刻意錯誤全部找到、正確版 0 誤報（含 Excel 寫出再讀回的往返測試；也可選擇 `samples/excel/` 的實際檔案再測一次）。Node 版：`npm test`。

## 法規更新：不改程式就能跟上新規定

主管機關調整申報格式或新增檢核時，系統改版往往趕不上，過渡期只能人工補齊；沒攔到的錯誤會被退件，甚至遭裁罰。工具頁尾的「法規更新」讓法遵或主管單位不必等 IT、也不需要 AI：

- **規則更新包**（JSON 檔）：新增檢查（可設前提條件與**適用起日**，例如只檢查 2025/07/01 以後生效的新契約）、在現有位置**定義新欄位**與允許的值（例如保留欄位改作新用途）、**停用**不再適用的內建檢查。匯入後立即套用，可隨時停用、移除或下載發給同事；結果、頁尾與報告都會註明套用了哪一版更新與依據文號。
- **表單新增**：選資料、欄位、條件，按「加入」馬上重新檢查，存成本機更新，可下載成更新包。
- **AI 轉換規則文件**（線上版）：上傳新版手冊或函令，由 AI 轉成檢查，試跑確認後再使用。

**自動跟上法規更動**（半自動，刻意保留人工確認）：

1. **每天自動監看**：GitHub Actions（`.github/workflows/regulation-watch.yml`）每天檢查 `rules/updates/sources.json` 列出的法規來源（全國法規資料庫的保險法、金管會保險局、保發中心公告），只比對含關鍵字的段落；有新公告時自動開一張待辦單，列出新增的段落與處理步驟。不需要 API key。
2. **法遵確認**：判斷是否影響申報，在「法規更新」頁建立更新包並試跑。
3. **自動發布到所有人**：更新包放進 `rules/updates/`、登記在 `rules/updates/index.json`，併入 main 後，每個人打開工具時自動套用最新版，畫面會提示一次；個人可以在本機關閉，但不能刪除官方更新。

**官方更新包的簽章與審核**：

1. **簽章金鑰（已產生）**：正式版本已固定公鑰指紋 `7fb780c45230b133`（`src/app.js` 的 `PACK_KEY_PINS`，公鑰在 `rules/updates/public-key.json`）。工具只套用這把公鑰對應的私鑰簽過的官方更新包，**不採用「第一次看到就信任」**：網站上的公鑰被換掉、拿掉，或不在固定清單裡，官方更新包一律不套用。CI 會檢查固定的指紋和公鑰是同一把。私鑰由核准法規更新的人保管，不可放進 repo。
   - **更換金鑰**（私鑰遺失或換人）：在自己的電腦執行 `node tools/pack-keygen.js ~/新的私鑰.pem`，把新的指紋填進 `PACK_KEY_PINS`、提交新的 `public-key.json`，經審核發布新版本；舊版本的工具不會接受新公鑰，要更新後才生效。
2. **發布**：`node tools/publish-pack.js rules/updates/<檔名>.json --key ~/dq-pack-signing-key.pem`，會檢查格式、登記 SHA-256 並簽章。
3. **開啟 GitHub 分支保護**：GitHub 的 repository → Settings → Branches → Add branch ruleset（或 Add rule），目標 `main`，勾選：
   - Require a pull request before merging，Required approvals 1，並勾 Require review from Code Owners（`.github/CODEOWNERS` 指定更新包、公鑰與驗證程式的負責人）
   - Require status checks to pass，選「檢查」（`.github/workflows/ci.yml`：自動測試與 `publish-pack.js --check`）
   - Block force pushes

   開啟後，任何人（包括管理者）都要經負責人審核、檢查通過才能合併到 main。

不讓程式直接依網頁內容改規則：法規文字需要解讀（適用對象、生效日、例外），未經確認就上線的錯誤規則可能擋下整批正確資料或漏抓錯誤。

格式說明在 `src/rule-packs.js`，示範檔 `rules/updates/example-2026-format-change.json`（假設保留欄位第 1 碼改為「數位投保註記」）。每筆資料總長度改變時仍需更新程式。

## 延伸

規則集與引擎分離。其他險種（傷害、癌症、年金）的填報手冊格式相近，各加一個 `src/rulesets/*.js` 即可沿用同一套介面、對帳、報告與 AI 分析；主辦單位提供正式檢核規則後，也只需調整規則集。
